\section{Problem: WCET of an Iterative Scan Matcher}
\label{sec:problem}

\subsection{The NDT align kernel}
% Brief NDT recap (Magnusson). Map = voxel grid of Gaussians (multi-tile: one grid per
% dynamically loaded map tile, kd-tree over all leaf centroids). Per align: Newton iterations;
% per iteration: transform P source points, radius-search neighbors, evaluate the
% score/gradient/Hessian kernel per (point, leaf) pair, solve a 6x6 system.
\ndt{} registration~\cite{biber2003ndt,magnusson2009thesis} compresses the reference map into a
voxel grid of Gaussians: each voxel with sufficiently many points stores the mean and
(eigenvalue-regularized) covariance of the points inside it. Aligning a scan then maximizes a
smooth likelihood --- each transformed source point scores against the Gaussian--uniform
mixture of its nearby voxels --- over the 6-DoF pose (translation plus Euler angles) by
Newton's method. One align call runs up to \texttt{max\_iterations} Newton steps; each step
transforms all $P$ source points, radius-searches the voxel-centroid kd-tree for each point's
neighbor leaves (radius equal to the voxel size), accumulates the score, gradient, and
$6{\times}6$ Hessian over every (point, leaf) pair, solves the Newton system, and selects a
step length by a More--Thuente-style procedure bounded by a configured maximum step. Iteration
stops when the pose update drops below a threshold $\epsilon$ or the iteration cap is hit. The
engine studied here is Autoware's production \emph{multigrid} variant of the multi-threaded
\texttt{ndt\_omp} implementation~\cite{autoware,ndtomp}: the map is loaded dynamically as
\emph{tiles} around the vehicle, each tile keeps its own voxel grid, and the kd-tree spans the
leaf centroids of all loaded tiles --- so overlapping tiles multiply the leaves a radius search
can return, a fact that matters for the worst case (Sec.~\ref{sec:implementation}). We analyze
the serial configuration (\texttt{num\_threads}=1), the deterministic baseline that a
worst-case bound must cover.

\subsection{Execution-time decomposition}
For one align call:
\begin{equation}
  T \;\le\; N_{\mathrm{iter}} \cdot \Bigl[\; \sum_{p=1}^{P} \bigl( T_{\mathrm{search}}(p) +
      K(p)\, T_{\mathrm{kernel}} \bigr) + T_{\mathrm{solve}} \Bigr],
  \label{eq:decomp}
\end{equation}
with exactly four data-dependent freedoms:
\begin{itemize}
  \item $N_{\mathrm{iter}} \le$ \texttt{max\_iterations} (static loop guard; default 30);
  \item $P$: source-cloud size --- a \emph{caller-side} bound (the node voxel-downsamples the
        scan); we fix $P = 2000$ except in the scaling study of Sec.~\ref{sec:eval-psweep},
        which validates that the bound is affine in $P$;
  \item $K(p) \le \maxnn = 64$: neighbor leaves per point (enforced search cap);
  \item kd-tree traversal length per query (worst case $O(N_{\mathrm{leaves}})$, geometry-dependent).
\end{itemize}
$T_{\mathrm{solve}}$ (fixed-size $6{\times}6$ SVD) and the per-point transform are
input-independent. Equation~\eqref{eq:decomp} is a \emph{work} bound; converting work to time is
platform-specific and is where measurement enters (Sec.~\ref{sec:methodology}).

\subsection{Why the bound is not enough}
% (a) the product P*K*iter is astronomically pessimistic if treated as independent maxima
% unless an input actually achieves it simultaneously -> need witness inputs;
% (b) constant factors (cache, allocator, subnormals) are not in the work model;
% (c) the C++ engine's per-point heap allocations put the allocator--an unbounded-latency
% component--inside the inner loop.
Three gaps separate \eqref{eq:decomp} from a usable bound. First, the individual maxima may not
be simultaneously achievable; a defensible bound needs \emph{witness inputs} that realize the
product. Second, constant factors are timing hazards invisible to the work model: cache
behavior, allocator latency, and floating-point assists on subnormal operands. Third, the
production C++ engine calls the heap allocator ${\approx}11$ times per point per derivative
pass (Sec.~\ref{sec:eval-alloc}), placing an unbounded-latency component inside the innermost
loop.
