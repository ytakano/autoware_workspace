\section{Problem: WCET of an Iterative Scan Matcher}
\label{sec:problem}

\subsection{The NDT align kernel}
\ndt{} registration~\cite{biber2003ndt,magnusson2009thesis} compresses the reference map into a
voxel grid of Gaussians: each voxel with sufficiently many points stores the mean and
(eigenvalue-regularized) covariance of the points inside it. Aligning a scan then maximizes a
smooth likelihood, in which each transformed source point scores against the Gaussian--uniform
mixture of its nearby voxels, over the six-degree-of-freedom pose (translation plus Euler
angles) by Newton's method. One align call runs up to \texttt{max\_iterations} Newton steps;
each step transforms all $P$ source points, radius-searches a kd-tree of voxel centroids for
each point's neighbor leaves (radius equal to the voxel size), accumulates the score, gradient,
and $6{\times}6$ Hessian over every (point, leaf) pair, solves the Newton system, and selects a
step length by a More--Thuente-style procedure bounded by a configured maximum step. Iteration
stops when the pose update drops below a threshold $\epsilon$ or the iteration cap is hit.

The engine studied here is Autoware's production \emph{multigrid} variant of the multi-threaded
\texttt{ndt\_omp} implementation~\cite{autoware,ndtomp}: the map is loaded dynamically as
\emph{tiles} around the vehicle, each tile keeps its own voxel grid, and the kd-tree spans the
leaf centroids of all loaded tiles. Overlapping tiles therefore multiply the leaves a radius
search can return, a fact that matters for the worst case (Sec.~\ref{sec:implementation}).
Throughout,
the \emph{engine} is this align kernel with its map structures; the \emph{node} is the ROS
component that feeds it (preprocessed scans, initial guesses from the localization filter, map
tiles) and consumes its poses. We analyze the serial engine configuration
(\texttt{num\_threads}=1), the deterministic baseline that a worst-case bound must cover.

\subsection{Execution-time decomposition and notation}
\label{sec:decomposition}
For one align call:
\begin{equation}
  T \;\le\; N_{\mathrm{pass}} \cdot \Bigl[\; \sum_{p=1}^{P} \bigl( T_{\mathrm{search}}(p) +
      K(p)\, T_{\mathrm{kernel}} \bigr) + T_{\mathrm{solve}} \Bigr],
  \label{eq:decomp}
\end{equation}
with $N_{\mathrm{pass}} = N_{\mathrm{iter}} + 1$,
where a \emph{derivative pass} transforms all $P$ source points and accumulates the score,
gradient, and Hessian: one initial pass evaluates the guess pose, then each Newton iteration
performs exactly one more at its trial step. The step-length procedure re-evaluates
derivatives \emph{only} in its More--Thuente refinement loop (up to 10 further passes per
iteration), which sits behind a \texttt{use\_line\_search} flag that the shipped
configuration disables and the port implements as the default (disabled) path. Hence
$N_{\mathrm{pass}} = N_{\mathrm{iter}}{+}1$ holds structurally, is machine-checked per input
(Sec.~\ref{sec:methodology}), and holds exactly on every fixture and every real frame of
Sec.~\ref{sec:eval-realdata}. The bound has exactly four data-dependent freedoms
(Table~\ref{tab:preconditions} in Sec.~\ref{sec:threats} collects each limit, its enforcer,
and the behavior on violation):
\begin{itemize}
  \item $N_{\mathrm{iter}} \le$ \texttt{max\_iterations}: the Newton iteration count (static
        loop guard; the shipped default is 30, hence $N_{\mathrm{pass}} \le 31$);
  \item $P$: the source-cloud size, a \emph{caller-side} bound (Autoware's shipped pipeline
        random-downsamples the scan to exactly $P \le 1500$ points); we use $P = 2000$ for the
        engine-level fixtures (a margin above the production cap) except in the scaling study
        of Sec.~\ref{sec:eval-psweep}, which validates that the bound is affine in $P$;
  \item $K(p) \le \maxnn = 64$: the number of neighbor leaves each point collects (a search cap
        the port enforces; Sec.~\ref{sec:implementation} derives why 64 suffices);
  \item the kd-tree traversal length per query (worst case $O(N_{\mathrm{leaves}})$,
        geometry-dependent).
\end{itemize}
$T_{\mathrm{solve}}$ (a fixed-size $6{\times}6$ solve) and the per-point transform are
input-independent. We write \sumnbr{} for the total number of (point, leaf) kernel evaluations
in an align call, \kdnodes{} for the total number of kd-tree nodes visited, and $\bar{K} =
\sumnbr / (\text{points processed})$ for the mean neighbor count per point; these are the
\emph{work counters} that Sec.~\ref{sec:methodology} turns into instrumentation.
Equation~\eqref{eq:decomp} is a \emph{work} bound; converting work to time is
platform-specific and is where measurement enters.

\subsection{Why the bound alone is not enough}
Three gaps separate \eqref{eq:decomp} from a usable bound. First, the individual maxima may not
be simultaneously achievable; a defensible bound needs \emph{witness inputs} that realize the
product. Second, constant factors are timing hazards invisible to the work model: cache
behavior, allocator latency, and floating-point behavior on extreme operands. Third, the
production C++ engine calls the heap allocator ${\approx}11$ times per point per derivative
pass (Sec.~\ref{sec:eval-alloc}), placing a component with unbounded worst-case latency inside
the innermost loop.
