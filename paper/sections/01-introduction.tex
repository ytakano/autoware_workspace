\section{Introduction}
\label{sec:intro}

Autoware~\cite{autoware} localizes a vehicle by aligning each light-detection-and-ranging (LiDAR) scan to a Gaussian
voxel map with the Normal Distributions Transform (\ndt)~\cite{biber2003ndt}. At 10\,Hz,
each alignment has a \SI{100}{ms} period before a late pose forces downstream estimation toward
dead reckoning. Yet input geometry changes Newton iterations, neighbor multiplicity, and
kd-tree traversal. Across the synthetic stress inputs, the lowest engine--fixture median is
\SI{\tailsMinMedian}{ms}, whereas the largest observed latency is
\SI{\tailsMaxObserved}{ms} on the same core, a \tailsLatencySpread-fold span. Nominal
replay therefore cannot answer whether the deadline has defensible margin.

Static and parametric worst-case-execution-time (WCET) analysis can express
input-dependent bounds, but this kernel
still requires a realizable geometry that jointly exercises its dominant terms. Exhaustive
enumeration is infeasible, while wall-clock-guided search is noisy and machine-specific. We
instead separate a structural work envelope from platform timing and search deterministic
work counters for stress witnesses.

Rust is useful here not because C++ cannot be bounded, but because ownership, lifetimes, and
aliasing rules discharge memory-safety and data-race-freedom obligations in the safe
core~\cite{jung2018rustbelt}. This narrows project-specific validation to equivalence,
numerics, work bounds, and timing. The reduction excludes the FFI, unsafe code, and trusted
dependencies. The port also builds as \texttt{no\_std} for real-time environments without
the standard library. Its radius query caps neighbors at \maxnn; the
\emph{bounded-neighbor domain} $D$ contains inputs whose uncapped queries already satisfy
that limit. Per-input work traces compare a defined work shape on evaluated inputs; leaf
payloads, traversal, memory operations, and latency are assessed separately.

Our objective is to make the \ndt{} align kernel amenable to real-time analysis through
explicit work limits and timing evidence. The Rust port is both an implementation and an
analysis instrument; the production C++ engine is its behavioral and timing baseline. We do
not search for or establish the C++ implementation's worst traversal shape.

Our contributions are:
\begin{enumerate}
  \item A three-layer analysis combining a property-tested structural work bound,
    deterministic stress-witness generation using Rust counters, and controlled timing of
    frozen witnesses.
  \item A per-input cross-language work-trace conformance check. The base-agreement set
    $E_{\mathrm{base}}$ checks iteration equality and pose and score tolerances;
    $E_{\mathrm{shape}}$ additionally checks the recorded
    pass structure, point and neighbor counts, and canonical leaf identities. A separate
    payload digest checks leaf means and inverse covariances. Neither establishes runtime
    membership in $D$ or full semantic equivalence.
  \item A domain-informed construction that reaches the configured maximum of
    \runtimeKernelEvalMax{} common kernel evaluations, together with two archived candidates that
    exercise high Rust kd-node counts at lower common-kernel work under the same timing
    protocol.
  \item An industrial case study in which Rust removes the C++ per-point allocation hazard
    within reserved capacities and has a smaller observed maximum on every paired fixture in
    the unified three-boot campaign. Contract-geometry and
    shipped-configuration witnesses separate production input constraints from
    configuration effects, while open- and closed-loop replays of a single drive expose
    the residual conformance boundary and engine-level recovery behavior.
\end{enumerate}

Section~\ref{sec:problem} defines the work model;
Secs.~\ref{sec:methodology}--\ref{sec:implementation} present the method and port.
Section~\ref{sec:evaluation} evaluates the evidence, followed by limitations, related work,
and conclusions. The appendix contains secondary diagnostics.
