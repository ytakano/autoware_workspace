\section{Implementation}
\label{sec:implementation}

% Keep this section tight: only what a reader needs to trust the numbers.
\subsection{The engines}
The C++ engine is Autoware's pcl-based, OpenMP multigrid
\ndt{}~\cite{autoware,ndtomp}. We measure its serial configuration with
\texttt{num\_threads}=1. The Rust engine is a port that can also build as
\texttt{no\_std}, without the standard library, so its computational core can run in
real-time environments where that library is unavailable, including the evaluated bare-metal
kernel deployment. Behind
the C ABI it exposes the same entry points as a drop-in replacement. The differential test
suite covers voxel-grid construction, align, engine, and end-to-end node paths and passes
with the Rust engine substituted.
Compiler versions and the measurement environment appear in Sec.~\ref{sec:eval-setup};
both engines were measured at autoware\_core commit \texttt{\envCommit}. The released
per-run manifests contain the binary hashes.

\subsection{WCET-relevant hardening of the Rust real-time path}
The following properties are explicit design and verification constraints of the port, not
automatic consequences of choosing Rust or \texttt{no\_std}.
\begin{itemize}
  \item \textbf{Zero allocation from the first frame}: all align buffers are pre-reservable
    to the worst-case sizes determined by $P$, \maxnn, and
    $N_{\mathrm{iter}}{+}1$. A counting global allocator asserts zero allocations
    \emph{including} the first frame. A growth event is a WCET spike, so amortized warmup
    is not a bound.
  \item \textbf{Recursion-free kd-tree}: the radius search runs an iterative walk over a fixed
    64-entry stack. The median build gives a depth of
    $\le \lceil \log_2 N \rceil{+}1$. The port preserves the exact near-then-far visit
    order because neighbor order determines floating-point summation order and therefore
    fidelity. This order is differential-tested against the recursive oracle. The
    iterative form measured ${\approx}\oneoffKdIterSpeedup\%$ faster than the recursive one
    in a same-day, same-core comparison.
  \item \textbf{Panic-free, lock-free}: lint-enforced absence of panicking operations on the
    real-time path. The align path takes no locks and instead reads a lock-free snapshot of
    the map state.
  \item \textbf{Zero-cost instrumentation}: counter increments are compiled out when the
    feature is disabled; the disabled build's synthetic frame-time baseline is unchanged.
\end{itemize}

\paragraph{Sufficiency of the neighbor cap}
The port caps the radius search at $\maxnn = 64$ where the C++ engine collects an unbounded
neighbor set; the cap is what makes the $P \cdot \maxnn \cdot N_{\mathrm{pass}}$
decomposition possible at all. Its value is justified geometrically. A leaf's centroid lies
inside its own voxel. Both engines' APIs couple the search radius to the voxel size, so the
search ball has diameter two voxels and thus intersects at most
three cells per axis: \emph{at most $3^3 = 27$ leaves per tile can ever be in range,
regardless of map content}. Under the disjoint-tile contract, leaf multiplicity is 1, so 27
bounds the global count and $\maxnn = 64$ carries a $2.4\times$ margin: truncation is
unreachable, so the equal-work precondition against the uncapped C++ engine holds for
every such input. Section~\ref{sec:eval-realdata} reports a measured maximum of
\realKmaxMax{} on a real map. This is one above the voxel-center heuristic of 8 and
comfortably inside the limit of 27.

Exceeding 64 requires at least three adversarially crowded \emph{overlapping} tiles, i.e.\
inputs that leave the comparison domain $D$ of Sec.~\ref{sec:meth-transfer}. There the Rust
engine truncates, keeping its cost bounded, while the C++ engine's cost grows without bound
with tile multiplicity: an asymmetry we report as a structural hazard of the uncapped
implementation, not as something this analysis bounds. Because truncation breaks equal
work, the equal-work assertion doubles as the runtime membership check for $D$.
\emph{Dense-neighbors} sits exactly at the cap with $8 \times 8 = 64$ in-range leaves and
passes, certifying that the
two engines still saw identical neighbor sets.

\subsection{Adversarial fixture construction for the engine tier}
\label{sec:impl-fixtures}
Four hand-built generators target one hazard each. \emph{Dense-neighbors} pins $K = \maxnn =
64$ using 8 overlapping map tiles whose voxel centroids crowd shared block corners: a single
tile geometrically caps $K$ at the ${\le}8$ voxels sharing a corner when the search radius
equals the leaf size, so tile overlap, which production dynamic map loading makes possible
in principle, is essential to reach the cap; this is why the frozen fixture format
stores its map as tiles. \emph{Max-iterations} is a rough random surface with
$\epsilon = 10^{-10}$ that does not converge within the configured iteration cap. \emph{Cache-hostile} scatters the source across a
wide map in shuffled order. \emph{Subnormal} places the source on a shell where the kernel's
$\exp$ lands in the \texttt{f64} subnormal range. The search of Sec.~\ref{sec:meth-search}
then composes and exceeds them.

\subsection{The deployment tier: preprocessing-legal worst cases}
\label{sec:impl-legal}
The fixtures above are \emph{engine-API-legal} but not \emph{preprocessing-reachable}. The
production pipeline voxel-downsamples the scan with a \SI{3.0}{m} leaf and no duplicate
points, caps it at $P = 1500$ through random downsampling, and crops it to
$\pm\SI{60}{m}$. The map
pipeline emits disjoint, voxel-aligned tiles from a downsampled map, which caps leaf
multiplicity at 1 and hence $K$ at the per-tile geometric ceiling of 27 derived above. The
voxel-center heuristic suggests at most 8 voxels sharing a corner, but real centroids can
lie anywhere inside their voxel; Sec.~\ref{sec:eval-realdata} observes
$K = \realKmaxMax$. These parameter values are Autoware's shipped localization defaults.
We therefore add a fifth
fixture, \emph{legal-worst}: the hardest such input we \emph{constructed}. It uses a single
tile whose per-voxel points are spaced to survive map downsampling. Their centroids lie
approximately at voxel centers and less than $2.0$ units from each lattice corner because
$\sqrt{3} < 2.0$. The fixture has $P = 1500$
duplicate-free source points on distinct lattice corners at \SI{4}{m} pitch inside the crop,
each collecting exactly $K = 8$, the voxel-center heuristic's maximum.
$\epsilon = 10^{-10}$ pins the iteration cap. Its counters certify
$\bar{K} = \legalWorstKbar$ against the engine-level 64. It is the tier's \emph{witness},
a constructed lower bound on the tier's worst case, while the tier's provable ceiling
remains $K \le 27$.

One axis of this fixture is deliberately \emph{not} production-parameterized: with the shipped
$\epsilon = 0.01$, its smooth lattice geometry converges in \oneoffLegalWorstProdEpsIters{}
iterations, so the fixture pins the iteration cap through $\epsilon$ instead. The cap
assumption is supported by a production-parameterized witness. Re-running the counter-guided search with the
\emph{parameters frozen to the shipped values} and every candidate checked against the
preprocessing contract by an independent legality verifier. The verifier checks one point
per downsample cell, the crop, $P$, and map-spacing invariants. The search found a fully
legal rough-surface geometry that
oscillates to the full \textbf{30 of 30} iterations at $\epsilon = 0.01$, frozen as
\emph{legal-osc}. The production node also ships an oscillation-count diagnostic over its
per-iteration pose array, machinery that exists precisely because non-convergence occurs in
the field, including feature-poor geometry, map mismatch, and coarse initialization guesses.

Within this search family the two worst axes resist combination. Reaching $K = 8$ requires a
smooth lattice that converges quickly, while oscillation requires roughness that scatters
centroids to $\bar{K} = \legalOscKbar$. The $\epsilon$-pinned \emph{legal-worst} has the
higher total cost and therefore remains the tier's hardest measured witness; \emph{legal-osc} is its
iteration-axis witness.
